# What carries over from `metastable-2`

Status: review, 2026-09. This document re-reads the previous checker effort (branch `metastable-2`, tip `87e0853aff`, and the provenance work already on `main`) against the constraints of the restart, and says what to reuse, what to rebuild, and what to drop. No code was run for it; every number quoted is from a design record or a witness module doc.

**Revision note.** The first version of this review told the checker to reproduce the witness harnesses' load-trigger windows and to read "the tail after a bounded perturbation", and it framed the corpus as pairs of twins the checker had to separate. Both framings were wrong. The trigger is how a human confirmed a label, and the checker's question is whether any schedule under a fixed input makes the program do disproportionate work; the corpus is a set of labeled programs, and the checker is judged by agreement with the labels. Sections 3 and 5 were rewritten and the rest adjusted.

## The constraints this review applies

1. The checker only has to work on idiomatic Hydro dataflow, where state lives in `use::state`, `use::state_null`, folds and keyed singletons, and logic lives in operators. Raft and every protocol written as one `by_mut` closure are out of scope.
2. The judge is the witness corpus (`design_docs/2026-09_witness_corpus_spec.md`): `rpc_retry` and the files under `hydro_test/src/cluster/witnesses/`, each carrying a label that a human confirmed with a stress harness. The harness's load trigger and its 800-round shape belong to the confirmation, not to the checker.
3. The end product is a deterministic tool that decides whether a unit has schedule-dependent work amplification and says where in the code the hazard arises, without a declared goal and without instrumenting the program.
4. Provenance, counterfactual replay, and an adversarial scheduler are mental models that may or may not be needed.

Two observations frame the rest.

**The checker's question is about schedules, not load.** Given a fixed input stream, does there exist a schedule, meaning a choice of which items each `use::batch` releases and when and which version each `use::snapshot` observes, under which the program does unboundedly or disproportionately more work than the productive minimum? The simulator's nondeterministic decisions are that search space, and the checker should drive them toward amplification directly. The old sweep did this: it perturbed one hook edge for the whole run under fixed inputs and compared work against the prompt run, and that is the right shape. A schedule that keeps a delivery late is a legal schedule, so the continuing perturbation was a strength, and the discriminator is whether the excess work grows with the adversity of the schedule (the delay grid) or saturates at a constant multiple. The corpus's benign criterion says the same thing in the harness's terms: total work is bounded by a small constant multiple of the input under every schedule explored.

**Several corpus programs have identical dataflow and differ only in a captured constant or a closure body.** `rpc_retry` with `max_attempts = 3` and with `1` differ by a constant. `bounded_queue_rejection` with `max_backlog = Some(100)` and with `None` differ by a constant (`None` becomes `usize::MAX` inside the placement closure, and the reject path exists in both). The request-dated and fill-dated caches differ by which field a `map` closure reads. Only the coalescing cache differs structurally, by one `filter_key_not_in(pending.keys()).first()` on the fetch path. So the verdict must come from behaviour, and static analysis can at most localize and prune.

## 2. What to port or rebuild, for each surviving technique

**Hold schedules and the empty-tick option.** Port `hydro_lang/src/sim/hold_schedule.rs` and `edge_counts.rs` from `87e0853aff` together, since `HoldScheduleDriver` reads `edge_counts::current_hook`. Both need the `SimHook` additions in `runtime.rs` (`edge_location`, `pending_release_len`, `buffered_len`, `pending_release_positions`) and the `run_hooks` changes in `compiled.rs`; `git diff main metastable-2 -- hydro_lang/src/sim/runtime.rs hydro_lang/src/sim/compiled.rs hydro_lang/src/sim/builder.rs` is about 430 lines, of which the lineage id plumbing (`pending_release_records`, `pending_release_ids`, `format_item_serialize`) can be left out. Nothing in these files knows about goals or Raft. The one change worth making on the way in is edge identity: a hook's location is the `sliced!` invocation plus an index, so two batches in one slice share a line, and the design record already asked for an operator id in the IR metadata.

**Per-edge counts.** Same commit, same port. Keep it passive and host-side as it is. Add nothing yet.

**The sweep, without a goal.** Port `sweep.rs` and keep its search as it is: every hook edge, a constant and a bursty move, a delay grid, fixed inputs, comparison against the prompt run. Change three things. First, the verdict column must not need `Program::goals`: start with per-edge counts against prompt, add the payload-shape column (the `Debug` rendering with digits stripped, already implemented in `counterfactual.rs`) as the program-knowledge-free answer to displacement, and read the verdict from how the excess behaves along the delay grid, since bounded amplification saturates and the hazardous kind keeps growing. Second, the move set needs release-size moves as well as release-timing moves; section 3 explains why a hold alone cannot exercise a server-side bound. Third, the driver has to work with the corpus's harness shape, which sends one clock element and a round's data and then calls `quiesce()`. Under the forcing rule a held delivery is forced out inside its own round, which is why the old harnesses sent the whole clock up front and metered it; under `with_empty_ticks_allowed` a hold is measured in hook decisions inside the quiesce loop, and nobody has checked that this behaves. This is the first experiment in section 5, because if it fails the checker needs its own metered-clock entry point, and `rpc_retry.rs` on `metastable-2` (lines 674 to 2026, dropped from the port) shows what that looks like.

**Derived goals instead of declared ones.** `lineage.rs::per_goal` (the boundary log, 802 lines, 17957c8674) is worth porting only if the identity pass supplies its extractor; otherwise the per-edge and per-shape counts do the same job.

**The identity pass.** Port `identity.rs` and `CompiledSim::operators()` (both in 87e0853aff) with the part of `lineage_pass.rs` that builds the operator table (`OperatorInfo`, the `negative` flag), which needs no record ids. Its outputs are a candidate goal extractor per edge (the key type of the keyed operator the edge feeds) and a static list of loci where the program tests absence or deduplicates, which is the starting set for both the sweep's candidate edges and the localization report.

**Lineage pass and negative leaves, later.** `lineage_pass.rs`, `lineage_rt.rs`, and the `per_goal_by_ancestry` and `re_derivations` methods of `lineage.rs` are the tool that names the operator. Leave them on the old branch until the verdict pipeline reproduces the corpus labels, then port them for the localization step only and pay the 103 s per run there.

**Counterfactual forks, later.** `counterfactual.rs` depends on `sweep::Program` and `Run`; port it after the sweep is re-shaped, and only as the second localization tool.

**One extra witness to consider.** `hydro_std/src/ec_inference_demos/multi_paxos_live.rs` on `metastable-2` is a simulator-runnable Multi-Paxos with a timer input and a measured redo-queue amplification (accept traffic 3.5 times prompt under bursty acks). Whether it is idiomatic enough for constraint 1 is the corpus author's call.

## 3. How the survivors would behave on each labeled program

This section reasons from mechanism; nothing was run. For each program the question is whether some schedule under the program's fixed input makes the per-edge or per-shape counts exceed the prompt run, and whether that excess grows along the delay grid or saturates.

**`rpc_retry`, `max_attempts = 3`, labeled amplifying.** Any schedule that holds responses past 40 ticks produces re-sends, and every re-send adds records to the arrivals, processed and responses edges without displacing anything. Under a continuing hold the old sweep measured 5,000 sends against 2,400 for the prompt run, and the excess grows with the hold length and then with the server queue the extra arrivals build. The identity pass names the `unique()` and `filter_key_not_in(responded_ids)` in the client slice but cannot label the program.

**`rpc_retry`, `max_attempts = 1`, labeled benign.** No schedule changes the send count, since the client never re-sends; holds only move completions later. Every per-edge count equals prompt under every move, which is the expected benign reading.

**`bounded_queue_rejection`, `max_backlog = Some(100)`, labeled benign.** Release-timing moves alone say nothing here: holding the responses edge at the client keeps the server's `backlog` state empty, so the bound never fires and the client re-sends exactly as `rpc_retry` does. The bound is exercised only when the server's own queue exceeds 100, which a hold cannot cause and a release-size move can: `Periodic { period: d }` on the arrivals edge releases `2d` requests into one server tick, the server rejects the excess, and the client re-sends after 10 ticks and is served once. The `processed` edge shows each id once and the excess saturates rather than growing with `d`. This program is why the move set must include release size.

**`bounded_queue_rejection`, `max_backlog = None`, labeled amplifying.** Under the same bursty arrivals the server queues everything and serves each request up to three times; the witness's measurement saw 667 of 1,000 ids served again. The `processed` edge excess grows with `d`, since a larger burst builds a longer queue and more timeouts.

**Cache with coalescing, labeled benign.** While a hot key is missing, the cache issues one fetch per key, so the fetches edge count under any hold or burst on the fetch or fill edges equals the number of keys that went missing, which is bounded by the input. Per-edge counts equal prompt up to convergence-time effects.

**Cache without coalescing, request-dated, labeled amplifying.** One fetch per lookup while the key is missing. A hold on the fills edge does not build an origin queue, so that move shows only the herd's bounded excess. A burst on the fetches edge does: `2d` fetches land at once against a capacity of 4 per tick, the last is served `d/2` ticks later, and once that exceeds the TTL of 20 the cache discards the fill as stale and re-fetches. The witness's own run saw the origin queue grow from 2,462 to 3,258 with all fills discarded. On the delay grid the fetches edge excess is flat below `d` of roughly 40 and grows without bound above it, which is the signature the verdict column should read.

**Cache without coalescing, fill-dated, labeled benign.** Same dataflow; the stale-fill test reads a different field. The herd's redundant fills each restart the key's TTL, so the origin queue drains and the excess (568 redundant fills in the witness's run) saturates at a multiple of the lookups per outage. The sweep will show a real but bounded excess on the fetches edge at every `d`, so the verdict must distinguish saturating excess from growing excess or it will label this program amplifying against the corpus. This is the program most likely to expose a weak verdict column.

**Gossip, labeled benign.** No retry, timeout or acknowledgement exists; every move changes convergence time and never the number of sends per pump, so per-edge counts equal prompt under every schedule. One caution: the deliveries land in a `TopLevelFoldHook`, which `Hold` never supported, so the port must either implement `Periodic` for it or record that the edge was not moved.

**W5, the election stampede, label pending.** This is the in-scope hard case. Its goal (a leader) is abstract, its messages carry a term that changes per attempt, and elections displace heartbeats, so per-edge totals may fall while it storms, as on Raft, and the identity pass will return the term, which is a stamp. The per-shape column (vote requests against heartbeats on one edge) is the only program-knowledge-free signal the old work found for this shape. Whether it ranks W5 is open until the witness lands.

## 4. What the localization requirement implies

The requirement is to say where in the code the hazard arises. The techniques differ in what they can name.

The sweep names an edge: the `use::batch` whose delayed or bursty release produced the excess, and the edges where the excess appeared. For `rpc_retry` that is the responses or arrivals hook and for the cache the fetches hook. It is a location the programmer can act on and needs no program knowledge, but it names the input to the loop rather than the operator that closes it.

The negative-leaf rule names the operator: the absence test whose output was re-derived while a delivery was held. On `rpc_retry` that is the `filter_key_not_in(responded_ids)` in the client slice, which is the retry decision itself. On idiomatic code this is exact and is the most precise answer available, at the cost of the lineage pass and its runtime.

The identity pass names candidates statically: every `unique`, anti-join, keyed fold and keyed state in the unit, with the key type. It cannot label a program, but it prunes the sweep (only edges feeding an absence test can manufacture work) and gives the report a place to point before any run.

Counterfactual forks name a delivery and list the records it caused. That explains one cell but is a poor substitute for the operator, because a storm has no single owner and on a totally ordered hook the fork releases the whole buffer.

Per-edge counts name edges only when compared across schedules; provenance labels, feedback campaigns and PerfFuzz give program-level verdicts and no location.

Two plumbing items follow. Edge identity must become an operator id in IR metadata, or the report will name a slice rather than a line. And the checker must find its edges from a compiled program without a harness declaring them, which `CompiledSim::operators()` does for operators and the prompt run does for hook edges.

## 5. Recommended order of experiments

Each experiment searches schedules under a fixed input, ends in a command run against the corpus, and has a pass criterion stated as agreement with the corpus labels. No experiment applies a load trigger; the input to every run is the witness's baseline workload. Cheapest first.

**E1. The round-based harness can hold.** Port `edge_counts`, `hold_schedule` and `with_empty_ticks_allowed`. Run `rpc_retry`'s baseline workload (2 requests per round) under `HoldScheduleDriver` holding the client's responses hook at `d = 41` for the whole run. Pass: total sends exceed the input, and the same run on `max_attempts = 1` sends exactly the input. Fail: `quiesce()` never returns, or the hold is flushed within its round; then the checker needs its own metered-clock entry point and the old `amplification_tests` harness is the model. This is plumbing, and it must pass before any verdict is trusted.

**E2. A release-timing move reproduces the `rpc_retry` label.** Same harness, the hold on responses at `d` on a grid from 8 to 128. Pass: `rpc_retry`'s excess sends grow with `d` and its server queue is non-decreasing at the end of the run, while `max_attempts = 1` shows no excess at any `d`. Fail: the excess saturates at the attempt cap and the queue drains, which means a hold alone does not build a server queue at capacity 5 under baseline load, and the release-size move of E3 is needed for this label too.

**E3. A release-size move exercises server-side bounds.** `Periodic { period: d }` on the arrivals hook, `d` on a grid from 8 to 64, on `bounded_queue_rejection` with `Some(100)` and with `None`, again under baseline workload. Pass: the unbounded program's `processed` edge excess grows with `d`, and the bounded program's saturates and its `processed` edge shows each id at most once. Fail at every `d`: scheduling alone cannot exercise the bound on this program, and the checker's move set is still missing something, which should be recorded before moving on.

**E4. The goal-free sweep on the corpus.** Port `sweep.rs` with the per-edge and per-shape columns, no `goals`, both move kinds, and a verdict rule that reads the delay grid: amplifying if some edge's excess keeps growing along the grid, benign if every edge's excess saturates or is zero. Run it on every labelled configuration under its baseline workload. Pass: every amplifying label (`rpc_retry`, unbounded queue, request-dated herd, and whichever of W3, W5, W8, W10, W11 land as amplifying) gets a growing excess on some edge, and every benign label (`max_attempts = 1`, bounded queue, both benign caches, gossip, the heartbeat and transitive-closure controls) gets none. The fill-dated cache decides the verdict rule, since its real excess must be read as saturating. Any miss names the missing move or the missing column.

**E5. The identity pass on the corpus.** Port `identity.rs` and the operator table, run without a simulation. Pass: `rpc_retry` and the bounded queue yield the request id, the cache yields the key for `entries` and `pending` and the lookup id for `waiting`, gossip yields the set element. Record what W5 yields; the prediction is the term, which is a stamp. This is a localization and pruning tool, and its output is not a verdict.

**E6. The shape column on W5.** Once W5 has a measured label, run E4's sweep with the payload-shape column. Pass: if W5 is amplifying, some cell ranks above prompt by shape even where its per-edge total is lower. Fail: W5 joins Raft as a case the program-knowledge-free verdict cannot rank, and the checker's report must say so.

**E7. Localization on the found cells.** For each amplifying cell from E4, run the lineage pass with negative leaves and, separately, forks at the held decisions. Pass: `rpc_retry` names the `filter_key_not_in` on responses and the cache names the miss path's fetch construction, and the two tools agree on the edge. This is the last experiment because it is the most expensive and because its output is only useful once the verdict is trusted.
