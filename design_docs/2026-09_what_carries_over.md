# What carries over from `metastable-2`

Status: review, 2026-09. This document re-reads the previous checker effort (branch `metastable-2`, tip `87e0853aff`, and the provenance work already on `main`) against the constraints of the restart, and says what to reuse, rebuild, or drop. No code was run for it; every number quoted is from a design record or a witness module doc.

**Revision note.** The first version of this review told the checker to reproduce the witness harnesses' load-trigger windows and to read "the tail after a bounded perturbation", and it framed the corpus as pairs of twins the checker had to separate. Both framings were wrong. The trigger is how a human confirmed a label, and the checker's question is whether any schedule under a fixed input makes the program do disproportionate work; the corpus is a set of labeled programs, and the checker is judged by agreement with the labels. Sections 3 and 5 were rewritten and the rest adjusted. A second revision followed the corpus's change to mechanism-based labels: a program is hazardous when some schedule makes the same input cost more work as delivery is delayed, whether or not a mitigation caps the damage, and benign only when no schedule creates work. The earlier verdict rule, which read excess that "saturates at a constant multiple" as benign, is withdrawn, and section 3 now carries the corpus's current labels.

## The constraints this review applies

1. The checker only has to work on idiomatic Hydro dataflow, where state lives in `use::state`, `use::state_null`, folds and keyed singletons, and logic lives in operators. Raft and every protocol written as one `by_mut` closure are out of scope.
2. The judge is the witness corpus (`design_docs/2026-09_witness_corpus_spec.md`): `rpc_retry` and the files under `hydro_test/src/cluster/witnesses/`, each labeled by mechanism and confirmed with a stress harness. The harness's load trigger belongs to the confirmation, not to the checker.
3. The end product is a deterministic tool that decides whether a unit has schedule-dependent work amplification and says where in the code the hazard arises, without a declared goal and without instrumenting the program.
4. Provenance, counterfactual replay, and an adversarial scheduler are mental models that may or may not be needed.

Two observations frame the rest.

**The checker's question is about schedules, not load.** Given a fixed input stream, does there exist a schedule, meaning a choice of which items each `use::batch` releases and when and which version each `use::snapshot` observes, under which the program does more work than the input requires? The simulator's nondeterministic decisions are that search space, and the checker should drive them toward amplification directly. The old sweep did this: it perturbed one hook edge for the whole run under fixed inputs and compared work against the prompt run, and that is the right shape. The verdict rule follows the corpus's definitions. A program is **hazardous** if, under some move on some edge, the extra work (records on an edge beyond the prompt run's count) rises as the imposed delay rises, and **benign** if the extra work is zero, or independent of the delay, under every move tried. A mitigation such as a retry cap, backoff, a queue bound or a compaction reserve makes the excess rise more slowly or plateau; it does not make the excess independent of delay. A capped or stepped curve that rises from zero is a hazardous reading, and only a flat curve is benign.

**Several corpus programs have identical dataflow and differ only in a captured constant or a closure body.** `rpc_retry` with `max_attempts = 3` and with `1` differ by a constant, and the second never re-sends. `bounded_queue_rejection` with `max_backlog = Some(100)` and with `None` differ by a constant (`None` becomes `usize::MAX` inside the placement closure). The request-dated and fill-dated caches differ by which field a `map` closure reads. Only the coalescing cache differs structurally, by one `filter_key_not_in(pending.keys()).first()` on the fetch path. So the verdict must come from behaviour, and static analysis can at most localize and prune.

## 2. What to port or rebuild, for each surviving technique

**Hold schedules and the empty-tick option.** Port `hydro_lang/src/sim/hold_schedule.rs` and `edge_counts.rs` from `87e0853aff` together, since `HoldScheduleDriver` reads `edge_counts::current_hook`. Both need the `SimHook` additions in `runtime.rs` (`edge_location`, `pending_release_len`, `buffered_len`, `pending_release_positions`) and the `run_hooks` changes in `compiled.rs`; the diff against `main` over `runtime.rs`, `compiled.rs` and `builder.rs` is about 430 lines, of which the lineage id plumbing (`pending_release_records`, `pending_release_ids`, `format_item_serialize`) can be left out. The corpus relabeling supplied the case for `with_empty_ticks_allowed` (5bb9bee46f): the bounded queue's `Some(100)` row could not be confirmed by a deterministic hold on the reply edge, because the server has no timer and `run_hooks` forces a tick whose only loaded hook is the replies hook to release something, so the witness fell back to reading delay off 512 fuzzed schedules. A checker that holds arbitrary edges needs the empty-tick option from the start. The one other change worth making on the way in is edge identity: a hook's location is the `sliced!` invocation plus an index, so two batches in one slice share a line, and the design record already asked for an operator id in the IR metadata.

**Per-edge counts.** Same commit, same port. Keep it passive and host-side as it is. Add nothing yet.

**The sweep, without a goal.** Port `sweep.rs` and keep its search as it is: every hook edge, a constant and a bursty move, a delay grid, fixed inputs, comparison against the prompt run. Change three things. First, the verdict column must not need `Program::goals`: start with per-edge counts against prompt, add the payload-shape column (the `Debug` rendering with digits stripped, already implemented in `counterfactual.rs`) as the program-knowledge-free answer to displacement, and read the verdict from how the excess changes along the delay grid. The rule is the one in the introduction: a rising excess is hazardous even if it later plateaus, and only a flat one is benign. Second, the move set needs release-size moves as well as release-timing moves; section 3 explains why a hold alone cannot exercise a server-side bound. Third, the driver has to work with the corpus's harness shape, which sends one clock element and a round's data and then calls `quiesce()`. Under the forcing rule a held delivery is forced out inside its own round, which is why the old harnesses sent the whole clock up front and metered it; whether a hold under `with_empty_ticks_allowed` behaves inside the quiesce loop is experiment E1. If it fails, the checker needs its own metered-clock entry point, for which `rpc_retry.rs` on `metastable-2` (lines 674 to 2026) is the model.

**Derived goals instead of declared ones.** `lineage.rs::per_goal` (802 lines, 17957c8674) is worth porting only if the identity pass supplies its extractor; otherwise the per-edge and per-shape counts do the same job.

**The identity pass.** Port `identity.rs` and `CompiledSim::operators()` (both in 87e0853aff) with the part of `lineage_pass.rs` that builds the operator table (`OperatorInfo`, the `negative` flag), which needs no record ids. Its outputs are a candidate goal extractor per edge (the key type of the keyed operator the edge feeds) and a static list of loci where the program tests absence or deduplicates, the starting set for the sweep's candidate edges and the localization report.

**Lineage pass and negative leaves, later.** `lineage_pass.rs`, `lineage_rt.rs`, and the `per_goal_by_ancestry` and `re_derivations` methods of `lineage.rs` are the tool that names the operator. Port them for the localization step only, once the verdict pipeline reproduces the corpus labels, and pay the 103 s per run there.

**Counterfactual forks, later.** `counterfactual.rs` depends on `sweep::Program` and `Run`; port it after the sweep is re-shaped, and only as the second localization tool.

**One extra witness to consider.** `hydro_std/src/ec_inference_demos/multi_paxos_live.rs` on `metastable-2` is a simulator-runnable Multi-Paxos with a timer input and a measured redo-queue amplification (accept traffic 3.5 times prompt under bursty acks); whether it is idiomatic enough for constraint 1 is the corpus author's call.

## 3. How the survivors would behave on each labeled program

This section reasons from mechanism; nothing was run. The labels are the corpus's current, mechanism-based ones, with "mitigated" appended when a knob prevents collapse. For each configuration the question is whether some move on some edge makes the per-edge or per-shape counts rise with the delay grid.

**`rpc_retry`, `max_attempts = 3`, hazardous.** Any schedule that holds responses past 40 ticks produces re-sends, and every re-send adds records to the arrivals, processed and responses edges without displacing anything; the old sweep measured 5,000 sends against 2,400 under a continuing hold. The excess is zero below the timeout and steps up at each multiple of it; the server at capacity 5 does not keep up, so the excess keeps rising. The identity pass names the `unique()` and `filter_key_not_in(responded_ids)` in the client slice but cannot label the program.

**`rpc_retry`, `max_attempts = 1`, benign.** No re-send exists, so no schedule changes the send count; holds only move completions later. Every count equals prompt at every delay, which is the flat curve.

**`backoff_retry`, backoff on, hazardous.** The witness measured re-sends of 2, 1,044 and 3,524 for triggers of 30, 60 and 90 rounds. Under a hold on responses the sends edge shows `rpc_retry`'s rising curve with the steps spread out geometrically; the slower rise is the mitigation. With backoff off the program is `rpc_retry`.

**`bounded_queue_rejection`, `max_backlog = Some(100)`, hazardous, mitigated.** A hold on the client's responses edge behaves as on `rpc_retry`: the server's queue stays empty, the bound never fires, and the sends edge rises after the timeout. The witness's confirmation found mean re-sends of 5.00, 5.78 and 8.20 across 512 fuzzed schedules as the longest reply delay grew from 2 to 4 ticks. The bound is exercised only by a release-size move: `Periodic { period: d }` on the arrivals edge releases `2d` requests into one server tick, the server rejects the excess, and the client re-sends and is served once, so the `processed` edge shows each id once while the sends edge still rises with `d`. The bound changes which edge carries the excess and how large it gets, not whether it appears. A checker that wants to describe the mitigation, and not only detect the hazard, therefore needs release-size moves to reach the server's queue.

**`bounded_queue_rejection`, `max_backlog = None`, hazardous.** Under bursty arrivals the server queues everything and serves each request up to three times (667 of 1,000 tail ids served again in the witness's run), so both the `processed` and the sends edges rise with `d`.

**Cache with coalescing, benign.** One fetch per missing key, so the fetches edge count under any move equals the number of keys that went missing, which the input fixes; the witness confirmed this under 256 fuzzed schedules.

**Cache without coalescing, request-dated, hazardous.** One fetch per lookup while the key is missing, so a hold on the fills edge makes the fetches edge rise from the first tick of delay. A burst on the fetches edge adds the collapse: `2d` fetches land at once against a capacity of 4 per tick, and once the last is served later than the TTL of 20 the cache discards the fill as stale and re-fetches (origin queue 2,462 to 3,258 in the witness's run).

**Cache without coalescing, fill-dated, hazardous, mitigated.** Same dataflow; the stale-fill test reads a different field. The witness's hold experiment measured 124, 160, 200, 272 and 498 fetches for the same 1,920 lookups as the origin's clock was withheld for 0, 5, 10, 20 and 50 rounds, with every lookup completing and the origin draining each time. That is a rising curve; the fill dating makes redundant fills restart the key's TTL, so the origin recovers, which is the mitigation. The first version of this review predicted "a real but bounded excess" here and told the verdict rule to call it benign; that described the plateau and missed the rise that reaches it.

**`gossip_resend`, re-send on, hazardous.** A delayed acknowledgement makes the sender re-send its deltas once per peer per tick, and each re-send costs the peer a merge from a bounded budget, which delays the peer's own acknowledgements (13,858 re-sends against 17,200 first sends in the witness's run). Under a hold on acknowledgements the sends edge rises from the first tick past `ack_timeout_ticks`; the per-tick cap fixes the slope, not the height.

**`gossip_resend`, `ack_timeout_ticks = 0`, benign.** No re-send exists (zero measured); a hold moves merges later and changes no count.

**`crdt_gossip_load`, benign.** No retry, timeout or acknowledgement exists; every move changes convergence time and never the number of sends per pump. One caution: the deliveries land in a `TopLevelFoldHook`, which `Hold` never supported, so the port must either implement `Periodic` for it or record that the edge was not moved.

**`election_stampede`, both configurations, hazardous.** The witness measured 353 elections with uniform timeouts, 128 with spread 3, and 173, 353 and 537 wasted elections for holds of 10, 20 and 30 rounds, so the curve rises in both configurations. It remains the hard case for the instrument rather than for the rule: elections displace heartbeats, so a per-edge total may fall while it storms, and the identity pass will return the term, which is a stamp. The per-shape column (vote requests against heartbeats on one edge) should still rise with the hold; whether it does is experiment E6.

W8, W10 and W11 had not landed on the branch at this revision.

## 4. What the localization requirement implies

The requirement is to say where in the code the hazard arises. The techniques differ in what they can name.

The sweep names an edge: the `use::batch` whose delayed or bursty release produced the excess, and the edges where the excess appeared (the responses or arrivals hook for `rpc_retry`, the fetches hook for the cache). It is a location the programmer can act on and needs no program knowledge, but it names the input to the loop rather than the operator that closes it.

The negative-leaf rule names the operator: the absence test whose output was re-derived while a delivery was held. On `rpc_retry` that is the `filter_key_not_in(responded_ids)` in the client slice, which is the retry decision itself. On idiomatic code this is exact and is the most precise answer available, at the cost of the lineage pass and its runtime.

The identity pass names candidates statically: every `unique`, anti-join, keyed fold and keyed state in the unit, with the key type. It cannot label a program, but it prunes the sweep, since only edges feeding an absence test can manufacture work, and gives the report a place to point before any run.

Counterfactual forks name a delivery and list the records it caused, which explains one cell but is a poor substitute for the operator, because a storm has no single owner and on a totally ordered hook the fork releases the whole buffer.

Per-edge counts name edges only when compared across schedules; provenance labels, feedback campaigns and PerfFuzz give program-level verdicts and no location.

Two plumbing items follow. Edge identity must become an operator id in IR metadata, or the report will name a slice rather than a line. And the checker must find its edges from a compiled program without a harness declaring them; `CompiledSim::operators()` does this for operators and the prompt run for hook edges.

## 5. Recommended order of experiments

Each experiment searches schedules under a fixed input and has a pass criterion stated as agreement with the corpus labels. No experiment applies a load trigger; the input to every run is the witness's baseline workload. Cheapest first.

**E1. The round-based harness can hold.** Port `edge_counts`, `hold_schedule` and `with_empty_ticks_allowed`. Run `rpc_retry`'s baseline workload (2 requests per round) under `HoldScheduleDriver` holding the client's responses hook at `d = 41` for the whole run. Pass: total sends exceed the input, and the same run on `max_attempts = 1` sends exactly the input. Fail: `quiesce()` never returns, or the hold is flushed within its round; then the checker needs its own metered-clock entry point and the old `amplification_tests` harness is the model. This must pass before any verdict is trusted.

**E2. A release-timing move reproduces the `rpc_retry` label.** Same harness, the hold on responses at `d` on a grid from 8 to 128. Pass: `rpc_retry`'s excess sends are zero below the timeout and rise with `d` above it, while `max_attempts = 1` shows no excess at any `d`; `backoff_retry` with backoff on rises more slowly. A curve that rises and then plateaus at the attempt cap is a pass.

**E3. A release-size move exercises server-side bounds.** `Periodic { period: d }` on the arrivals hook, `d` on a grid from 8 to 64, on `bounded_queue_rejection` with `Some(100)` and with `None`, under baseline workload. Pass: both configurations show excess sends rising with `d`, the unbounded program's `processed` edge excess rises with `d`, and the bounded program's `processed` edge shows each id at most once. Both labels are hazardous; the experiment checks that the move set can reach the server's queue, which the localization report needs in order to say what the bound does. Fail at every `d`: the move set is still missing something, which should be recorded before moving on.

**E4. The goal-free sweep on the corpus.** Port `sweep.rs` with the per-edge and per-shape columns, no `goals`, both move kinds, and the verdict rule from the introduction: hazardous if some edge's excess rises along the delay grid under some move, benign if every edge's excess is zero or independent of the delay under every move. Run it on every labelled configuration under its baseline workload. Pass: every configuration labeled hazardous in section 3 (and whichever of W8, W10, W11 land as hazardous) gets a rising excess on some edge, and every benign one (`max_attempts = 1`, the coalescing cache, `gossip_resend` with re-send off, `crdt_gossip_load`, the heartbeat and transitive-closure controls) gets none. The fill-dated cache checks the rule's reading of a plateau: its curve rises from 124 to 498 fetches and then the origin drains, and the checker must call it hazardous. Any miss names the missing move or the missing column.

**E5. The identity pass on the corpus.** Port `identity.rs` and the operator table, run without a simulation. Pass: `rpc_retry` and the bounded queue yield the request id, the cache yields the key for `entries` and `pending` and the lookup id for `waiting`, gossip yields the set element. Record what W5 yields; the prediction is the term, which is a stamp. This is a localization and pruning tool, not a verdict.

**E6. The shape column on W5.** Run E4's sweep on `election_stampede` with the payload-shape column. Pass: some cell's vote-request shape count rises with the hold even where the edge's total falls because heartbeats were displaced. Fail: W5 joins Raft as a case the program-knowledge-free verdict cannot rank, and the checker's report must say so.

**E7. Localization on the found cells.** For each hazardous cell from E4, run the lineage pass with negative leaves and, separately, forks at the held decisions. Pass: `rpc_retry` names the `filter_key_not_in` on responses and the cache names the miss path's fetch construction, and the two tools agree on the edge. This is last because it is the most expensive and its output is only useful once the verdict is trusted.
