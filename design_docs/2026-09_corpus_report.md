# The witness corpus and what the checker prototype found on it

The corpus exists to give the amplification checker something it can be wrong about. It is a set of twelve small Hydro programs, written in idiomatic dataflow with every timer taken as an input stream, so that the simulator owns time and can explore schedules. Most programs carry one knob that changes the mechanism under study, which gives twenty-two configurations in all. Each configuration carries a label: **hazardous** if some schedule can make the program do work its input did not require, with the excess growing as delivery is delayed; **hazardous, mitigated** if that is so but a parameter keeps the program from collapsing under the harness's load burst; and **benign** if work is bounded by a function of the input under every schedule. The programs live in `hydro_test/src/cluster/witnesses/`, with `rpc_retry` one directory up because it is also the deployed ground truth, and the spec they were written to is `design_docs/2026-09_witness_corpus_spec.md`.

A label and a verdict are different things. A label is ground truth, set by the witness author's own harness before the checker existed, using one of four methods described in each section below. A verdict is what the checker prototype said when pointed at the same configuration. The prototype (`checker_experiments.rs`, driver in `hydro_lang/src/sim/hold_one_hook.rs`) knows nothing about any program. It runs each configuration under the workload its harness uses as the healthy steady state, with no burst, for 240 rounds; it discovers every `use::batch` hook that ever has something buffered; it holds each hook in turn, from round 20, for 0, 5, 10, 20, 40, 60, 80 and 100 rounds while every other decision follows the deterministic prompt schedule; and it reads work from the program's own output counters. The number reported for each hold is the work in the held run minus the work in the unheld run on the same input, so any positive number is work the schedule created. The verdict is hazardous if any hook at any hold length shows a positive gain, and benign otherwise. The hook with the largest gain is the location the checker reports. Two simulator changes were needed, both inert unless a hold is set: a hook now identifies itself to the driver, and a tick whose only buffered input is held parks instead of being forced to release. All twenty-two runs finish together in just under six minutes.

The four methods by which labels were established are referred to below by letter. Method (a) is collapse or recovery under a load burst on the deterministic schedule: 800 rounds of light steady load with a burst in rounds 100 to 160, and the tail (rounds 600 to 800) read for backlog growth and completions. Method (b) is a closed-form work count that holds exactly under hundreds of random schedules. Method (c) is withholding input elements (usually a program's clock) from the harness for k rounds and then redelivering them at once, on a fixed input with no burst, and reading how work varies with k. Method (d) is random-schedule fuzzing with the longest delay read off each run and work bucketed by it. Method (c) matters for how much the agreement is worth, because it is the closest of the four to what the checker itself does, and the summary classifies every label by its method.

## `rpc_retry`: a request/response service with timeout and retry

The client tags each application request with an id, keeps a table of requests awaiting a response, and re-sends any request unanswered within `timeout_ticks` (40), up to `max_attempts` sends in total, after which it reports the request abandoned. The server holds incoming requests in a FIFO and serves at most `max_per_tick` (5) per tick, answering each one. Time enters through a client clock stream and two metrics-window streams; a deployment wires `source_interval` into them and the simulation feeds them from `sim_input`. This is the one program in the corpus that has also been run deployed, and its module is the model every other witness followed.

It was created first because timeout-and-retry is the canonical metastable failure, and because it could be confirmed both in simulation and on a machine. Two configurations are labeled.

With `max_attempts = 3` the label is hazardous, established by method (a). Under the deterministic schedule the harness offers 2 requests per round against a capacity of 5 (40 percent utilization), then 12 per round in rounds 100 to 160. The burst builds a backlog of about 420, a queueing delay of about 84 rounds against the 40-round timeout, so every request is sent three times and offered load becomes 6 per round against a capacity of 5 after the burst has ended. In the tail the backlog grows from 1038 to 1237 and never shrinks, completions are 0 against a baseline of 400, and the server serves 667 already-served ids against 333 new ones. The deployed run showed the same shape: 800 retries per second and zero completions per second from 14 seconds onward. A control with retries armed and no burst stays at zero backlog with 2 completions per round throughout.

With `max_attempts = 1` the label is benign, established by method (a) as recovery: the same burst peaks the backlog at 420 and it drains to zero by round 300, with no re-sends and no repeated serves anywhere in 800 rounds.

The checker found both. At three attempts, holding the client's `Response` hook gave a curve of 0 0 0 0 0 80 160 320, which is exactly the hand computation (nothing until the hold exceeds the 40-tick timeout, then two requests per round each re-sent once and served again, doubling at 80 when second re-sends begin). Holding the server's `Request` arrivals hook gave 0 0 0 0 4 136 498 588, the largest gain, because held requests time out, their re-sends queue behind the held originals, and the dump on release keeps queueing delay above the timeout for many more rounds. The clock hook and the four metrics-window hooks were flat at zero. The verdict is hazardous, localized to the arrivals edge first and the response edge second, and it agrees with the label. At one attempt every one of the seven hooks read zero at every hold length, the verdict is benign, and it agrees.

## `backoff_retry`: the same client with exponential backoff and jitter

The program is the `rpc_retry` design with one change: with `backoff` set, the wait before send k+1 is `base_timeout_ticks << k` plus a jitter in `[0, base/2)` derived from a hash of the request id, so retry load decays geometrically and re-sends spread out. With `backoff` unset every wait is the base timeout and the program is `rpc_retry` exactly.

It was created to test the definition on the standard mitigation. Backoff is what practitioners add to stop retry storms, and the question was whether a program with backoff should be labeled benign because it recovers, or hazardous because the timer still fires. Under the corpus definition it is hazardous by mechanism, and the author was asked to confirm that and to report whether some burst size defeats backoff.

With `backoff = true` the label is hazardous, mitigated, established by method (a) with the burst length varied. Under the standard 60-round burst the run recovers: tail completions are 400 of 400, the backlog is last non-zero in round 646, and over 1000 rounds the client puts 2600 first sends and 1044 re-sends on the wire, so total work is 1.40 times the input. The author's hand estimate had recovery around round 580; the difference is that the one re-send per request also applies to the 720 requests issued during the burst. Varying the burst length gives 2, 1044 and 3524 re-sends for bursts of 30, 60 and 90 rounds, and at 90 rounds the re-sends exceed the first sends and 1134 of them are still queued or abandoned at round 1000, so backoff bounds the rate of redundant work per request and not the amount a schedule can cause.

With `backoff = false` the label is hazardous, established by method (a): the run reproduces `rpc_retry` and collapses with the same numbers (tail completions 0, backlog 1038 to 1237).

The checker found both hazardous. With backoff on, the server `Request` arrivals hook gave 0 0 0 0 0 90 242 448, a slower rise than `rpc_retry`'s because the second re-send waits 80 ticks rather than 40. With backoff off it gave `rpc_retry`'s curve exactly, 0 0 0 0 4 136 498 588. Both verdicts agree with their labels.

## `bounded_queue_rejection`: the same service with a bounded server queue

The client is the `rpc_retry` client with one addition: a request the server rejects is re-sent after `reject_backoff_ticks` (10) rather than after the timeout, and a rejection counts as one of the request's `max_attempts` sends. The server, after serving its `max_per_tick`, drops the oldest requests beyond `max_backlog` and answers each with a rejection in the same tick. With `max_backlog = None` the program is `rpc_retry` exactly.

It was created to test the definition on the other standard mitigation, server-side load shedding. A queue bounded at less than `timeout_ticks * max_per_tick` keeps the server's own queueing delay below the client's timeout, so a queued request is served once and an unqueued one learns so immediately. The bound cannot cap delay the network imposes, and a reply held past the timeout still produces a redundant send and a redundant serve, so the program is hazardous by mechanism.

With `max_backlog = Some(100)` (a server delay of at most 20 ticks against a timeout of 40) the label is hazardous, mitigated, established by method (a) for the recovery and by method (d) for the hazard. Under the standard burst the server never serves an id twice in 800 rounds; over the run the client sends 3033 times for 2200 requests, 1968 are served, 1065 rejected and 232 abandoned after three rejections, the queue peaks at 100 and is empty from round 250, and the tail is at baseline. The hazard itself could not be shown by withholding a timer, because the server has no timer and the simulator, as it stood then, forced a tick to release something from its only loaded hook. The author instead fuzzed 512 schedules of a 24-request run with four clock elements per round, a timeout of 2 and the bound never reached, and read the longest reply delay off each run: 511 of 512 schedules re-sent, the worst cost 41 sends and 41 serves for 24 requests, and mean re-sends grew with the longest delay a schedule imposed, 5.00 at 2 ticks, 5.78 at 3 and 8.20 at 4.

With `max_backlog = None` the label is hazardous, established by method (a): the run is `rpc_retry`'s run (tail completions 0, queue 1038 to 1237, 978 abandoned).

The checker found both hazardous. With the bound, the server `Request` arrivals hook gave 0 0 0 0 4 204 400 634, steeper than `rpc_retry`'s because rejections re-send after 10 ticks rather than 40; without it, `rpc_retry`'s curve. Both verdicts agree. The checker's ability to hold the reply edge here at all rests on the second of its two simulator changes, since this is the configuration whose author found holds impossible.

## `cache_thundering_herd`: a read-through cache in front of a slow origin

The cache keeps a table of keys and the tick from which each entry's age counts. A lookup on a present, unexpired key completes at once; a lookup on a missing or expired key waits and the cache asks the origin, which holds fetches in a FIFO and answers at most `max_fetch_per_tick` (4) per clock element. When a fill arrives, every waiting lookup on that key completes and the entry is written if the fill is still fresh. There are two knobs. `coalesce` decides whether the cache keeps a set of keys with a fetch outstanding and sends one fetch per missing key, or sends one fetch per missing lookup. `request_dated` decides whether an entry's age counts from the tick the fetch was issued (the conservative rule of RFC 7234, under which a fill older than the TTL on arrival is stale and answers waiting lookups but is not stored) or from the tick the fill arrived (under which every fill, redundant or not, gives the key another TTL of life). Time enters through a cache clock and an origin clock.

It was created because the thundering herd is a metastability pattern with a well-known one-operator fix, coalescing, so the corpus could contain a hazardous program and a benign program that differ in exactly one place. The dating knob was added by the author when the first design, fill-dated, failed to collapse. The harness uses ten hot keys walked round-robin at 8 lookups per round, a TTL of 20 ticks, an origin capacity of 4 fetches per round (baseline fetch load about 0.5 per round), and a burst of 10 lookups per round on never-repeated cold keys in rounds 100 to 160.

With `coalesce = false, request_dated = true` the label is hazardous, established by method (a). In the tail the origin is offered 1600 fetches against a capacity of 800, applies 0 fills and discards 800 as stale, and its queue grows from 2462 to 3258. The lookups themselves still complete at baseline (1600, mean latency 0.8), because a lookup waiting on key k is answered by the stale fill of an older fetch for k; the amplification is entirely in the origin's work.

With `coalesce = false, request_dated = false` the label is hazardous, mitigated, established by method (c). Under the burst this configuration recovers (origin queue peaks at 680 and drains, 568 redundant fills over the run, tail at baseline), because the redundant fills for a key arrive spread over the queueing delay and each restarts the key's life, so no new fetches are issued while the queue drains. The hazard was shown by withholding the origin's clock for k rounds from round 100 and redelivering it at once, over 240 rounds of the 1920-lookup baseline input with no burst: the origin was asked for 124, 160, 200, 272 and 498 fetches for k of 0, 5, 10, 20 and 50, where 124 is what the distinct misses require. Every lookup completes and the origin drains in every case; only the work differs.

With `coalesce = true` the label is benign, established by method (b): under 256 fuzzed schedules fetches never exceed distinct misses, and under the burst the origin queue peaks at 390 and drains with 100 fills for 100 fetches in the tail.

The checker found all three. Request-dated without coalescing, holding the cache's `Fill` hook (fills arriving from the origin) gave 336 388 468 2520 2668 2668 2668 2668; the jump between 10 and 20 rounds is where the held fills' age crosses the TTL of 20 and every fill becomes stale. Fill-dated without coalescing, holding the origin's clock hook gave 248 320 400 544 856 1152 1448 1748, a steady rise with no plateau. With coalescing, every curve was flat or falling (the `Fill` hook read 240 240 240 240 220 200 180 160, which is total work under a hold that only postpones fetches past the end of the run), so the verdict is benign. All three agree. For this program the checker's work measure was total fetches with the requirement taken as zero, so the shape of the curve carries the verdict, and the coalescing curve's fall is the signature of postponement rather than creation.

## `compaction_falls_behind`: a single-process store whose compaction is background work

The store receives a totally ordered stream of `Put` and `Get` operations into a FIFO. Each clock element grants `budget_per_tick` (30) units. Serving a `Put` costs one unit and appends a record to the uncompacted segment; serving a `Get` costs one unit plus one unit per record in the segment at the start of the tick. The store serves in FIFO order while the units spent are below the budget, always serving at least one operation, and compaction moves records from the segment into the index at one unit each using whatever budget is left. The knob `compaction_reserve` takes that many units off the top of every tick for compaction before any operation is served.

It was created to test whether the definition covers a single process with no network. The spec's sketch had a non-incremental compaction that blocks appends; the author replaced it with the read-cost coupling above, because in the sketch every record is appended once and scanned once, total work is a fixed two units per record under every schedule, and nothing feeds back.

With `compaction_reserve = 0` the label is hazardous, established by method (a). The harness offers 1 `Put` and 4 `Get`s per round, then 1 `Put` and 40 `Get`s in rounds 100 to 160. Once a `Get` costs more than a whole tick the store serves one or two reads per round however light the load, reaches a put about once every twenty rounds, and never has a unit left for compaction. In the tail it serves 205 operations against a baseline of 1000, spends 6805 units serving and 0 compacting, and its backlog grows from 3432 to 4223.

With `compaction_reserve = 8` the label is hazardous, mitigated, established by method (c). Under the burst it recovers (backlog peaks at 703 in round 159 and is empty from round 189, the segment never exceeds 6). The hazard was shown by withholding the operations, not the clock, for k rounds from round 100 and delivering them together, on a put-heavier input of 3 `Put`s and 2 `Get`s per round for 300 rounds with no burst: extra units beyond one per operation and one compaction unit per put were 0, 4, 52, 102 and 195 for k of 0, 4, 8, 16 and 32. The author's module docs note explicitly that under the corpus mix of one put per four gets the reserved store's surcharge is exactly zero at every hold, because that mix never puts more than six puts in one tick, which is why the hold runs use the heavier mix. Without the reserve the same experiment gives 0, 40, 30625, 28181 and 23581, so a hold of eight rounds alone tips the unreserved store into permanent collapse with no burst.

The checker found the first and missed the second. With no reserve, holding the `Op` arrivals hook gave 0 5136 9979 9281 7961 6741 5621 4601: a large jump at a five-round hold and then a decline proportional to the rounds remaining, which is what a program looks like once a hold has tipped it into a state it does not leave. The verdict is hazardous and agrees. With a reserve of 8, both of the program's hooks read zero at every hold length. The verdict is benign and disagrees with the label. The reason is mechanical and matches the author's own note: the checker used the corpus baseline of 1 `Put` and 4 `Get`s per round. Holding the clock under that input starves the tick of budget and then delivers the withheld elements as one tick whose reserve compacts the whole segment before any get is costed, and holding the operations dumps them into a store whose segment the reserve keeps at zero. The label's evidence came from a different input, one with three puts per round, and from withholding operations rather than a batch hook. Whether the reserved store deserves the hazardous label is therefore a question about whether the definition should quantify over inputs as well as schedules; the checker as built quantifies over schedules for one given input.

## `crdt_gossip_load`: a load harness for the existing full-state G-Set gossip

The program is `hydro_std::ec_inference_demos::crdt_gossip::g_set_gossip`, unmodified and imported. Each member folds its own updates and everything it receives into a set; a new local update is broadcast to every peer at once, and on every `gossip_ticks` element a member re-broadcasts its whole set to every peer. The program exports only the set, so the harness observes every version of each member's set and derives wire work from its size.

It was one of the two witnesses that existed before the corpus, and the spec asked for a load harness because it had only ever been tested for convergence. It is the benign control for gossip: there is no retry, timeout or acknowledgement anywhere, so a held message can delay convergence but cannot cause an extra send.

Its single configuration is labeled benign, established by method (b). With three members, one update per round dealt round-robin and a pump at every member every round, the elements a member puts on the wire in a round are at most `(n-1)(updates + |set|)`, and the merges per member per round are `3|set| - 2`, both determined by the input alone; the measured tail growth of wire work is a constant 6 per round. Under 256 fuzzed schedules every member's set is a subset of the union at every observation and equals it after every quiescence. The run is 120 rounds rather than 800 because the simulator's cost is quadratic in the set size; an 800-round attempt did not finish in an hour.

The checker found it benign. Over a 60-round run with holds of 2, 5, 10 and 20 rounds on the pump hook, total merges read 16113 15744 15123 13908 10803, falling as the hold grows, which is postponement of merges past the end of the run and not creation. The verdict agrees.

## `election_stampede`: heartbeat-timeout leader election

Five members run a leader election with no log. Member 0 starts as leader in term 1 and sends a heartbeat to every other member on each of its timer elements. Every member keeps a FIFO inbox of heartbeats, vote requests, vote grants and client requests, and processes at most `budget_per_tick` (3) of them per timer element. A follower or candidate that has processed no valid heartbeat for `election_timeout` (6) ticks increments its term, votes for itself, and sends a vote request to every peer; a member grants its vote to the first request it processes for a term higher than any seen; a majority makes a leader. Client requests carry no protocol meaning and cost one unit of budget each. The knob `timeout_spread_ticks` makes member i wait `election_timeout + i * spread`.

It was created to stand in for Raft, whose election storms are the textbook metastability example, in a form small enough that the state machine is a plain function applied to the messages the budget admits while the inbox, budget and timeout live in the dataflow. The spec expected uniform timeouts to split the vote indefinitely.

With `timeout_spread_ticks = 0` the label is hazardous, established by method (a) with the burst length varied. The burst is 30 client requests per member per round in rounds 100 to 120 (the author found the burst had to exceed budget times timeout minus one, or 17 requests per round, because a late heartbeat still resets the timer). Heartbeats wait behind the client requests, every follower's timeout fires in the same tick, and all become candidates for the same term. Over 800 rounds there were 353 elections and 1412 vote requests against a requirement of zero, the inbox total peaked at 2828, and the cluster was leaderless until round 579 at term 80. Varying the burst length gives 173, 353 and 537 elections for 10, 20 and 30 rounds. The expectation that uniform timeouts would split the vote forever was overturned: the members are not perfectly symmetric, so once the inboxes drain a candidate eventually wins.

With `timeout_spread_ticks = 3` the label is hazardous, established by method (a): 128 elections and 512 vote requests, settled by round 497 at term 51. The spread shortens the storm and does not prevent it.

The checker found both hazardous. Holding the `Msg` inbox hook gave 0 0 45 125 245 385 530 655 with uniform timeouts and 0 0 5 40 100 155 220 265 with a spread of 3, where work is vote requests plus elections. Both verdicts agree, and the spread configuration's shallower curve matches its shorter storm.

## `gossip_resend`: delta gossip with re-send until acknowledged

Every member of a five-member cluster keeps a G-Set. Each local update is sent as a one-element delta to every peer. A receiver keeps unmerged deltas in a FIFO inbox and merges at most `max_merges_per_tick` (5) per timer element, acknowledging each. A sender keeps every delta sent to a peer in an outstanding table until acknowledged, and on each timer element, per peer, re-sends the oldest outstanding delta if it has waited at least `ack_timeout_ticks`. Merges are idempotent, so a re-sent delta costs one unit of merge budget and one more acknowledgement and changes nothing else.

It was created as the hazardous counterpart of the full-state gossip: the same idea with an acknowledgement and a re-send added, so the corpus contains gossip both ways.

With `ack_timeout_ticks = 3` the label is hazardous, established by method (a). Baseline is 1 update per member per round (20 deltas on the wire per round), with a burst of 2 per member per round in rounds 100 to 160. Over 800 rounds the members made 17200 first sends and 13858 re-sends; the inbox total grew from 8584 to 11569 between rounds 600 and 800, by 15 per round exactly as the arithmetic in `sim_tests` predicts, and half of every tail merge was of a delta already merged.

With `ack_timeout_ticks = 0` the label is benign, established by method (a) as recovery together with exact counts: zero re-sends, every delta merged once per member, inbox peaks at 911 and is back to the in-flight level of 10 by round 338.

The checker found both. Holding the `Ack` hook with re-sends on gave 0 100 7063 7065 7065 7065 7065 7065, where work is re-sends plus repeated merges; the plateau is the program's cap of one re-send per peer per tick, which fixes the rate once the storm is self-sustaining. With re-sends off every hook read zero. Both verdicts agree.

## `lease_renewal_storm`: clients renewing leases against one server

Twenty clients each hold one lease. Every `renew_every_ticks` (10) ticks of its clock, offset by member id, a client sends a `Renewal` and keeps it in an outstanding table until the server's `Ack` arrives; a renewal still outstanding when the next period begins is superseded. The server keeps every job in a FIFO, serves `max_per_tick` (5) per clock element, and acknowledges each renewal served. A second server input carries unrelated jobs that share the FIFO, and the harness uses it as the burst. The knob `resend_after_ticks`, when `Some(g)`, makes a client re-send an outstanding renewal on every tick once it is g ticks old.

It was created because renewal storms are a metastability pattern with periodic rather than request-driven load, and because the mitigation, one outstanding renewal per client, is a clean removal of the mechanism rather than a damping of it.

With `resend_after_ticks = Some(4)` the label is hazardous, established by method (a) and confirmed by method (c). The burst is 12 other jobs per round in rounds 100 to 160. In the tail zero renewals are acknowledged against a baseline of 400, the clients send 400 first renewals and 2400 re-sends, all 4000 client ticks are spent with a lapsed lease, and the backlog grows from 5117 to 6908. The hold experiment withheld the server's clock for k rounds from round 100 with no burst: extra sends were 0, 0, 2, 30, 2311 and 2334 for k of 0, 2, 4, 8, 16 and 32, so a hold of 16 rounds alone leaves a backlog deep enough to sustain the storm for the rest of the run.

With `resend_after_ticks = None` the label is benign, established by method (a) as recovery together with exact counts: 1600 sends for 1600 periods over the run, steady state again from round 339, and zero extra sends at every hold length in the same hold experiment.

The checker found both. Holding the client's `Ack` hook with re-sends on gave 0 12 3345 3495 3495 3495 3495 3495, where work is renewals re-sent plus re-sends served; the plateau is the same fixed-horizon effect seen in gossip. With one outstanding renewal every hook read zero. Both verdicts agree.

## `pure_heartbeat_load`: a load harness for the existing pure heartbeat

The program is `hydro_test::cluster::pure_heartbeat`, unmodified. On every element of its timer, each of three members broadcasts one fixed-size heartbeat to every member over `broadcast_closed`. There is no acknowledgement, no retry, no state on the work path, and nothing that reads what arrived.

It was created as the simplest benign control: work is exactly n messages per timer element whatever the scheduler does.

Its single configuration is labeled benign, established by method (b) with a hold check alongside. Under the burst (member 0 pulsed twelve times per round in rounds 100 to 160) messages per round went 9, 42, 9 and every member received exactly the elements sent in every one of 800 rounds, 9180 messages for 3060 elements. Withholding member 0's timer for 0, 4, 16 or 64 rounds and releasing it gave 2700 messages for 900 elements at every hold, and under 256 fuzzed schedules the total received was always n times the elements sent.

The checker found it benign, and found something else too: the program has no `use::batch` hook at all, so there was nothing to hold. Its single measurement was 2160 heartbeats received for 720 timer elements over 240 rounds, and the verdict is benign for want of any schedulable decision. The verdict agrees.

## `rebalancing_ping_pong`: workers rebalancing on stale queue-length reports

Two workers receive tasks into FIFOs and process them at `work_per_tick` (5) units per clock element, one unit per task. On every element of `report_tick` a worker broadcasts its queue length; on every element of `clock` it compares its own length with each peer's last report and, if longer by more than `threshold` (10), migrates half the difference from its tail to the shortest such peer. Admitting a migrated task costs the receiver one unit before it processes anything. The knob `cooldown_ticks` forbids a second migration to the same peer within that many ticks. The harness pumps `report_tick` every `report_every` rounds, so that ratio is the staleness of the reports.

It was created because rebalancing on stale information is an amplification pattern in which the extra work is migration rather than retries, and the spec expected the same tasks to bounce between two workers indefinitely. The spec's proposed mitigation, per-item hysteresis, was replaced by the author with a per-peer cooldown, because in a two-worker system a peer that wants to send back can always send its own original tasks instead of the ones it just received.

With `cooldown_ticks = 0` and reports every 4 rounds the label is hazardous (the author's table says "hazardous, recovers"), established by method (a) with the report period varied. The burst gives worker 0 twelve tasks per round in rounds 100 to 160. Over the run there were 537 migrations and 126 tasks completed after bouncing at least twice, against 195 migrations and 0 bounces with fresh reports every round; the cluster drained by round 276 and the tail was at baseline. Across report periods of 1, 2, 3, 4, 6 and 8 the migrations were 195, 196, 391, 537, 366 and 620 and the bounced tasks 0, 0, 68, 126, 61 and 179. The expected collapse did not happen because a worker's own length is fresh even when its peer's is stale, so the loop is biased but stable.

With `cooldown_ticks = 8` the label is hazardous, mitigated, established the same way: 246 migrations and 0 bounced tasks at every report period.

The checker found both hazardous, through the same hook and with nearly the same curve. Holding the `u64` task arrivals hook gave 0 74 112 60 120 185 240 300 with no cooldown and 0 18 42 60 120 180 240 300 with a cooldown of 8, where work is migrations. Both verdicts agree with their labels, but the agreement here is thinner than elsewhere: a delayed dump of tasks onto one worker causes migrations under either configuration, and the checker sees that without seeing the difference between the ping-pong the cooldown removes and the legitimate moves it leaves. The label and the verdict agree for different reasons.

## `transitive_closure_load`: a load harness for the existing semi-naive transitive closure

The program is `hydro_test::local::productive_tc`, unmodified. Each element of `graphs` admits one finite edge set, each element of `steps` performs one semi-naive iteration (join the frontier with all edges, drop duplicates and known facts, make the survivors the next frontier), and a trace stream reports candidates generated, rejected and novel per iteration.

It was created as the benign control for high work: the recursion generates many intermediate tuples, including duplicates when a graph has several paths between the same pair, but every candidate is a path in the admitted graph, so the work to reach the closure is fixed by the input. It guards against a checker that mistakes a lot of work for amplified work.

Its single configuration is labeled benign, established by method (b). Baseline is a chain of 4 edges every 5 rounds; the burst admits a layered graph of 27 edges with 81 join candidates, 54 of them duplicates, in every round from 100 to 160. Over the run there were 2212 edges, 5748 candidates and 4720 facts, every number matching the hand computation, and under 256 fuzzed schedules no schedule exceeded the candidate bound. The harness also found that 212 of the 256 schedules produced fewer candidates than the closure requires, because the program replaces its frontier with each tick's novel facts and a tick that admits a graph without a step token discards the pending frontier. That is a completeness bug in the unmodified program, outside this project's scope, and it does not affect the label because it is a shortfall of work rather than an excess.

The checker found it benign. Holding the step hook gave 288 288 282 270 246 222 198 174 candidates, flat and then falling as iterations are postponed past the end of the run. The verdict agrees.

## Summary

The checker's verdicts agree with the labels on 21 of 22 configurations. Of the twelve programs, it named a location for every hazardous one, and in each case the hook it named is the edge a person would name from the mechanism: the server's arrivals hook and then the client's response hook for the three request/response programs, the fill edge or the origin clock for the cache, the acknowledgement hook for delta gossip and for lease renewal, the message inbox for the election, the task arrivals for rebalancing, and the operation arrivals for compaction. The three programs with no mechanism (full-state gossip, heartbeat, transitive closure) and the three configurations whose knob removes the mechanism (one attempt, re-sends off, one outstanding renewal) all read zero or falling on every hook.

The one disagreement is `compaction_falls_behind` with `compaction_reserve = 8`, labeled hazardous, mitigated and found benign. The two sides used different inputs. The author's hold evidence used 3 puts and 2 gets per round and withheld operations from outside; the checker used the corpus baseline of 1 put and 4 gets per round and held a batch hook inside. The author's own docs state that under the 1:4 mix the reserved store's surcharge is exactly zero at every hold, which is what the checker measured. So the disagreement is not about whether extra work exists but about which inputs the label may range over. Under the corpus definition as written (some schedule, for the given input) the checker is right about the input it was given; under a reading in which the label may pick the input, the author is right. That decision belongs to the definition.

A second observation bears on how much the 21 agreements are worth. The checker's method is to delay one edge and watch work grow. Labels established by method (c) were produced by delaying a clock or an input stream from outside and watching work grow, which is the same experiment with the perturbation applied one layer out. Agreement on those labels is therefore weaker evidence than agreement on labels established by a load burst on the deterministic schedule or by a closed-form count under random schedules, neither of which involves a hold. Two labels rest on method (c) alone (the fill-dated cache and the reserved compaction), and one of those two is the disagreement. Two more (the re-sending lease client and the heartbeat) used method (c) as a confirmation alongside a primary method that does not involve holds.
