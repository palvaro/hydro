# Task: write and label new witness programs for schedule-dependent work amplification

This brief is self-contained. Everything you need is in this file and in the repository's source code. You will be told below exactly which files you may not read.

## 1. The task

Write at least six new small Hydro programs, each of which may or may not be vulnerable to schedule-dependent work amplification, and for each one write a simulation harness that establishes a label. Each program goes in its own file under `hydro_test/src/cluster/witnesses/blind/<name>.rs`, declared with a `pub mod <name>;` line in `hydro_test/src/cluster/witnesses/blind/mod.rs`, and the `blind` module is declared with a `pub mod blind;` line in `hydro_test/src/cluster/witnesses/mod.rs`. You create the `blind/` directory and its `mod.rs`. The programs must be different in kind from the ones already in the repository, which cover timeout-and-retry request/response, a read-through cache with TTL expiry, delta gossip with acknowledgements, full-state gossip, heartbeat-timeout leader election, lease renewal, queue rebalancing between workers, log compaction, a pure heartbeat, and a transitive closure. Directions you might take, without any of them being prescribed, include flow control or credit-based protocols, publish/subscribe fan-out with slow subscribers, two-phase commit with participant timeouts, replicated log catch-up, rate limiters, work queues with visibility timeouts, membership or failure detectors, distributed locks, batching with both size and time thresholds, and sagas with compensating actions. At least two of your programs must be ones you believe are not vulnerable, and you must argue that belief as section 3 describes.

## 2. Definitions

A program is **hazardous** when there exists a schedule under which the same input causes the program to do work the input did not require, and the excess grows the longer delivery is delayed. A schedule is the set of choices the simulator makes about which buffered items each tick admits and when it admits them; the input is everything the harness sends, including timer elements. Work means messages put on the wire, items served, records processed, or any other countable unit of what the program does.

A program is **benign** when its total work is bounded by a function of its input under every schedule. Delay may postpone work and reorder it, but it cannot create it.

The hazard typically arises when a program reacts to the absence or lateness of a message by generating more messages or more work: a client that re-sends because a reply has not arrived, a follower that starts an election because a heartbeat is late, a cache that issues another fetch because the fill has not landed. The extra work then competes for the same capacity as the work that was already late, which makes the next message later still, and the loop closes. A program with no such reaction, whose every emission is caused by an input rather than by the lack of one, has nothing for delay to amplify.

## 3. Label bases

Exactly two bases are accepted for a label.

A configuration is **hazardous, by exhibited collapse**, when a test on a fixed deterministic schedule runs many rounds of light steady load, applies a bounded trigger for a bounded window, removes the trigger, and then shows in the tail of the run, long after the trigger ended, that redundant work persists. The trigger is a burst of extra input, or a window during which the harness withholds timer elements that it later delivers. Redundant work persisting means the backlog is still growing, or completions are at or near zero against a healthy baseline, or a storm of messages is still running. The test asserts on the tail numbers, and the assertion is the proof. A storm that lasts hundreds of rounds after a twenty-round trigger counts as a collapse; a system that recovers within a few dozen rounds does not.

A configuration is **benign, by assurance argument**, when you have written, in the module docs, an argument that total work equals a closed-form function of the input under every schedule, and you have checked that closed form by asserting it under a few hundred random schedules with `fuzz` and under the deterministic schedule with a burst applied. The argument may rest on the structure of the dataflow, for example that no operator in the program can emit a message except in direct response to an input element, but it must be written down and the closed form must be asserted.

No other basis is accepted. A program that recovers under one burst is not thereby benign. If a program you expected to collapse recovers, you should first try a longer or larger trigger, or a trigger placed differently, to find a collapse. If you become convinced it cannot collapse, write the assurance argument. If you achieve neither, label the configuration **unresolved** and say in the module docs what you tried and why neither basis was reached. An unresolved label is an honest outcome and is preferred to a label without a basis.

## 4. Simulator facts you need

The simulator lives in `hydro_lang/src/sim/`. The facts below are taken from the current code and you may verify each against it.

There is no clock. The simulator has no clock source, so `source_interval` and `sample_every` cannot run under it. Every timer your program uses must be a stream parameter, of type `Stream<(), L, Unbounded, TotalOrder, ExactlyOnce>` where `L` is the process or cluster that owns the timer, and each element on that stream is one tick of the timer. A deployment wires `location.source_interval(period)` into the parameter. A simulation creates the stream with `location.sim_input::<(), TotalOrder, ExactlyOnce>()`, which returns a tuple of a sender and the stream, and the harness sends elements on the sender. `Process::sim_input` (defined on the `Location` trait in `hydro_lang/src/location/mod.rs`) returns `(SimSender<T, O, R>, Stream<T, L, Unbounded, O, R>)`; `Cluster::sim_input` (in `hydro_lang/src/location/cluster.rs`) returns `(SimClusterSender<T, O, R>, Stream<...>)`, and a cluster sender takes a member id with each element. Data inputs are created the same way with the data's type in place of `()`.

Logical time is a fold over the timer. A program that compares times, for a timeout or an expiry, keeps a counter in Hydro state that advances by one per timer element and stamps items with its current value. The existing programs do this with `use::state(|l| l.singleton(q!(0u64)))` and `enumerate()` on the clock stream. Wall-clock reads are not allowed in the dataflow.

All mutable state lives in Hydro operators. Tables, queues, counters, and sets must be `use::state`, `use::state_null`, folds, `KeyedSingleton`s, or other Hydro live collections carried across ticks. A program that keeps state in Rust cells captured by `q!` closures is not a valid witness even if it runs, because the simulator cannot see or vary what happens inside such a cell.

Every `use::batch` is a scheduling decision. Inside a `sliced!` block, `use::batch(stream, nondet!(/** why varying this batch is legal */))` admits into the tick some prefix (for `TotalOrder` streams) or some subset (for `NoOrder` streams) of what has been delivered to that stream so far, and the simulator chooses which. `use::snapshot(singleton, nondet!(...))` chooses which version of a singleton the tick observes. These are the only points where the schedule enters a program. The `nondet!` comment should say what varying the batch can and cannot change about the program's behaviour.

Sends deliver immediately. A `send` or `broadcast_closed` or `demux` over `TCP.fail_stop().bincode()` places each item into the receiver's top-level channel as soon as the sender emits it. Network delay exists in the simulation only as the receiver's `use::batch` admitting the item in a later tick. Only the `fail_stop` transport is supported by default; `lossy_delayed_forever` is available under `test_safety_only()` and is not needed here.

A tick with nothing buffered does not run. A `sliced!` block none of whose batches has an item waiting is not runnable, so a periodic job that should run even when no data has arrived must be pumped by a timer element.

`hydro_lang::sim::quiesce().await` runs the scheduler until nothing can make progress. Inputs sent after it returns never interleave with work that happened before it.

The round pattern. A stress test loops over rounds. In each round the harness sends one element on each timer that should advance in that round, sends the round's data, awaits `quiesce()`, and drains every output. Outputs are exported from the program with `stream.sim_output()` on a process (returning `SimReceiver`) or `stream.sim_cluster_output()` on a cluster (returning `SimClusterReceiver`). `SimReceiver` offers `next().await`, `try_next().await` (returning `Option`), `collect::<Vec<_>>().await`, and `collect_sorted::<Vec<_>>().await`; the `SimClusterReceiver` versions take a member id as their first argument. Unordered outputs should be read with `collect_sorted`, so map them to `Ord` types. `SimSender` offers `send(item)` and `send_many(iter)` for `TotalOrder` inputs and `send_many_unordered(iter)` for `NoOrder` inputs; `SimClusterSender` offers `send(member_id, item)`, `send_many(iter of (member_id, item))`, and `send_many_unordered`. The harness records what it drained into a per-round record and asserts on the vector of records after the loop.

Running. `flow.sim()` on a `FlowBuilder` returns a `SimFlow` (in `hydro_lang/src/sim/flow.rs`). `flow.sim().run_prompt(async move || { ... })` runs one deterministic execution in which every batch admits everything buffered and ready ticks run in a fixed round-robin order; its numbers are reproducible, and it is the schedule for collapse tests. `flow.sim().fuzz(async || { ... })` runs the closure repeatedly under random schedules; bound it with `.unit_test_fuzz_iterations(k)` before `.fuzz`, and note that under plain `cargo test` a modest number of random executions is performed. `flow.sim().exhaustive(async || { ... })` enumerates every schedule and is feasible only for very short runs; it returns the number of executions explored. Cluster programs need `.with_cluster_size(&cluster, n)` before running, and a program that calls `assert_has_consistency` needs `.skip_consistency_assertions()`.

Practical findings from earlier authors. The test module `mod sim_tests` is staged into a separate crate when the program is compiled for simulation, so any `impl` block, helper struct, or free function that a `q!` closure refers to must be a `pub` item at module level in the program file, not inside `mod sim_tests`. A `bool` captured by a `q!` closure and used as an `if` condition does not splice; choose behaviour by building different dataflow at construction time, or pass a `u32` flag. Closures passed to `fuzz` must be `RefUnwindSafe`, so accumulate across iterations with atomics rather than `RefCell`. A type named inside a `q!` closure must be imported at module level with a `use` line, because the staged crate does not see function-local imports. Free functions called from inside `q!` should be named by full `crate::` path. Under `run_prompt` the order of ticks within a round is fixed but is not necessarily the order you would guess, so write assertions about steady state from measured numbers rather than from an assumed tick order. The simulator's cost can be quadratic in the size of state that is re-emitted every tick, so a program that broadcasts its whole state each round may need a shorter run.

## 5. Program requirements

Each program is a `pub fn` that takes its locations, its data input streams, its timer streams, and a small configuration struct, and returns a struct of output streams. The body should be idiomatic Hydro dataflow of under about 300 lines, with the mechanism visible in the dataflow rather than inside a large `q!` closure, so that a reader can point at the operator or `sliced!` block where the behaviour lives. Each program has explicit capacity parameters (items served per tick, fan-out bound, credit window, and so on) and takes its load from the harness rather than generating it. Each program exports enough outputs that work can be counted from outside: every message put on the wire, every item served or processed, completions with their latency in ticks, and a per-tick pending-work measure such as backlog depth. The harness distinguishes first-time from repeated occurrences by id, so ids must be assigned inside the dataflow, for example with `enumerate()` on an arrival-ordered stream. Every timer is an input. The module docs say how a deployment would wire `source_interval` into each timer parameter. Programs are not modified to make tests pass; if a test fails, the test or the label changes.

## 6. Test requirements

Every program file ends with a `#[cfg(test)] mod sim_tests`. The module contains a round record struct, a `run(...) -> Vec<Round>` function that builds the flow, wires `sim_input`s for every parameter, exports every output, and executes the round loop under `run_prompt`, and the tests described here.

Before any test is run, write the hand-computed expectation as a doc comment on the workload constants: the baseline load, the capacity, the trigger size and duration, the backlog the trigger should build, the delay that backlog implies against any timeout or expiry, and the offered load the mechanism will produce after the trigger. Write it first; if measurement disagrees, keep both and explain the difference.

For a configuration you label hazardous, the main test runs long enough to separate the trigger from the tail (the existing programs use 800 rounds with the trigger in rounds 100 to 160 and assert on rounds 600 to 800), asserts that the pre-trigger window is healthy, and asserts the tail condition from section 3. For a configuration you label benign, the tests assert the closed form for total work under `run_prompt` with the burst applied and under `fuzz` for a stated number of iterations, and the module docs carry the argument.

Every program has at least one control: the same run with the trigger removed must stay healthy throughout.

Each module's docs begin with a table giving, for every configuration, the baseline per round, the capacity, the trigger, any timeout or expiry, the tail numbers the tests assert on, the label, and the label basis. The table must reflect the numbers the tests assert on.

Tests should complete within a few minutes each. If a design is too slow for the simulator at the intended length, shorten the run and say so in the docs.

## 7. Process

Run `cargo check -p hydro_test --tests` before running tests. Run tests as `cargo test -p hydro_test --lib witnesses::blind > "$TMPDIR/blind.log" 2>&1` and read the log with `grep -E "test result|round |tail|panicked" "$TMPDIR/blind.log"`; do not stream test output into your context and do not rerun a long test to re-read output that is already in a log. Building may need `SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk` in the environment. Do not run stable `cargo fmt`, because `rustfmt.toml` uses nightly options. macOS has no `timeout` command. Escape `!` when typing macro names such as `nondet!` into a shell. Never edit crate sources while a simulator test is running. Make one commit per program, in Conventional Commits format with a Markdown body that carries the measured tail numbers, and commit only when the program's tests pass. Write all prose, in code comments and in commit messages, in complete sentences.
